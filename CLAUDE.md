# Sentinel

## Project overview

Sentinel is an open-source AI code review GitHub Action.
It runs on pull requests, sends the diff through a pipeline of specialist reviewers and a synthesizer built on Claude, and posts (or updates) a single review comment with the findings.
Each run also emits an observability trace to `traces/`, which a static GitHub Pages dashboard renders.

Stack:

- TypeScript, compiled/bundled with tsup.
- `@anthropic-ai/sdk` for calling Claude.
- `@octokit/rest` for GitHub API access.
- `zod` for validating any data that crosses a system boundary (API responses, action inputs, webhook payloads).
- `vitest` for tests.

## Conventions

- Strict TypeScript. No `any`, ever. Use `unknown` plus narrowing or a Zod schema instead.
- Validate all external data (GitHub API responses, Claude responses, action inputs) with Zod at the boundary. Do not trust unvalidated shapes past that boundary.
- Prompts are not inline strings in source code. They live in `prompts/` as versioned `.md` files and are loaded at runtime.
- Markdown docs (this file, `docs/`, `README.md`): one full sentence per line. Normal Markdown structure (headings, lists, code blocks) is preserved; just don't wrap multiple sentences onto one physical line.
- Commits follow Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, etc.).
- Never add an AI agent as a co-author on commits.

## Current scope

Sentinel is past the walking-skeleton stage.
Phase 1 (single-call reviewer) and Phase 2 (three parallel specialists plus a synthesizer) are complete, and an observability dashboard ships the run traces to GitHub Pages.
See `ROADMAP.md` for the full phase history and `docs/DECISIONS.md` for the architecture decisions behind each step.

The pipeline today, end to end:

- `src/index.ts`: entry point that wires the run together and emits an observability trace to `traces/{runId}.json`.
- `src/github.ts`: fetch a PR diff, post a review comment, and update it idempotently on subsequent runs instead of posting duplicates.
- `src/context.ts`: token estimation, per-file classification (lockfiles, generated files, and Sentinel's own `traces/` output are skipped), and diff truncation at 50k tokens with a truncation notice.
- `src/orchestrator.ts`: runs the three specialist reviewers (`src/reviewers/base.ts`) concurrently, each forced to return schema-validated findings via the shared `submit_review` tool (`src/review-call.ts`, `src/review-tool.ts`).
- `src/synthesizer.ts`: an LLM-judge pass that merges, ranks, and filters the specialists' findings, with merge/drop counts derived deterministically in code.
- `src/render.ts`: renders the synthesized review into the GitHub comment, sanitizing model output.
- `src/trace.ts`: the v2 trace format the dashboard consumes; its Zod mirror lives in `dashboard/src/data/schema.ts`, and the two must stay in sync.
- `prompts/*.md`: the specialist and synthesizer prompts, loaded at runtime. Prompts are authored by Javier, not generated by the agent.

## Next phase (Phase 3)

Phase 3 is not started.
Its planned scope is a routing step, one-hop import context, and a diff-unchanged short-circuit; the eval harness (originally Phase 4) is being pulled forward so routing and the specialist set can be judged on measured data rather than intuition.
Do not build ahead of the agreed scope, and confirm with Javier before starting the next phase.

## Keeping these docs true (phase-close ritual)

These steering documents are load-bearing: an agent takes `CLAUDE.md`, `ROADMAP.md`, and `docs/DECISIONS.md` at face value, so stale guidance actively misdirects work.
Treat updating them as part of the definition of done for every phase, not an afterthought:

- When a phase ships, update this file's "Current scope" and "Next phase" sections and the file list so they describe what actually exists.
- Add an ADR to `docs/DECISIONS.md` for any non-obvious architectural decision, and a `ROADMAP.md` entry recording what was built and its known limitations.
- Where a prose claim and code must agree (for example a threshold stated in a prompt and enforced in code), prefer a test that fails on drift over a comment that quietly rots.
